# AgentChat local client

Requires Python 3.10+. Codex, Claude Code and Antigravity must be installed and authenticated on this machine. The ordinary bridge uses only Python's standard library.

Managed Antigravity tasks and model-list queries disable the CLI's detached auto-updater with `AGY_CLI_DISABLE_AUTO_UPDATE=true` in that child process only. This prevents idle model refreshes from opening Windows Terminal and keeps running sessions on a stable executable. Update Antigravity explicitly with `agy update` while its sessions are idle; ordinary interactive launches and other harnesses retain their own settings.

Read `skills/agentchat-setup/SKILL.md` for setup. The web app saves the room's workspace/project selection and explicit roles on the server, then copies a short setup link. New profiles default to inheriting the manager's working directory and owning project name; unchecking this option reveals manual fields. There are no default production roles.

After setup, the owner can say **帮我重连** in the original local setup conversation. The installed setup skill locates the saved bridge, checks its process and connection, starts it only if stopped, and verifies local/server heartbeats while preserving all session identities. No fresh invitation is needed. This restores connectivity; interrupted model work still follows manager recovery, and an already-online bridge is retained. Both setup/reconnect and chat skills are installed in the workspace's `.agents/skills`, `.claude/skills`, and `.agent/skills` directories.

```text
python agentchat.py doctor
python agentchat.py connect --link-stdin
```

Provide the full `/setup/<request-id>#token=...` URL on stdin, or omit `--link-stdin` for a hidden prompt. The client fetches the configuration, registers the deputy and sessions, starts the bridge, waits for heartbeats and acknowledges completion. The server posts one notice and invalidates the invitation; existing member credentials remain valid. Keep the complete link out of argv and logs.

If interrupted, resume with the same link and `--config <returned-path>`. If only the final response was lost, use `finish-setup --config <path>`; repeating it does not rotate a newer invitation or post duplicate notices. The legacy `setup --server <base> --workspace <path> --roles <file> --start` still accepts a join token through its hidden prompt, stdin or environment, but has no invitation acknowledgment.

Every role requires `name`, `harness`, `role`. Names support Chinese and Latin letters. Supported harnesses: `codex`, `claude`, `antigravity`, `deepseek`, `command`.

The agent executing `connect` becomes the private manager; the web role list only contains workers. The client reuses an existing manager, otherwise binds the creator's exact current native conversation before registering workers. Codex's `CODEX_THREAD_ID` is detected automatically. Other harnesses can supply their own metadata using `--manager-harness HARNESS --manager-native-id ID` or `--manager-identity /local/identity.json`. The latter accepts harness, native_id, workspace, project_name and model/adapter metadata (no credentials or permission overrides). Custom commands should include `{session_id}` to resume the exact conversation. Missing identity is an explicit setup error, never a guessed installed harness or a replacement native conversation. Old invitations and manual legacy setup retain their original behavior.

For inherited setup, Codex resolves the exact thread's cwd and owning project from local metadata. Claude can resolve cwd from its exact transcript. Other metadata can be supplied by the setup agent with `--manager-workspace ABSOLUTE_PATH --manager-project-name PROJECT_NAME`; use the actual owning project name, not the chat title. A directory-based harness with no separately named project uses the directory basename. The command's own cwd (possibly the downloaded client directory) is never used to guess the workspace. Initial claim freezes the resolved workspace and project name for retries; use the original `--config` to reuse an existing manager. The bridge config and all newly registered session contexts record the selected project name. New inherited invitations require the bundled current client; older manual invitations remain compatible.

The manager alias defaults to `manager`, with a suffix if needed. Its messages and quotes are visible only to the human owner and that manager. Public broadcasts exclude it. Its own `MANAGER.md` documents `manage --member NAME --action models|configure|enable|disable|refresh-models`; configure accepts model, effort and timeout. Workers cannot access these controls or private history. Manager scratch files have a separate workspace, while same-harness native sessions share the project root. Antigravity sessions reuse the manager's existing native project ID; Codex and Claude use the common cwd. Finish the original setup turn before using the manager through group chat. Shared native conversations must not run concurrently from desktop and bridge; Codex can use independent storage as described below.

Codex Desktop may retain an active writer even when a chat is idle. `python agentchat.py codex-login` prepares a separate AgentChat Codex home and starts an ordinary, independent login; use the same account as Desktop. It never copies a rotating desktop refresh token. The default directory is `%LOCALAPPDATA%/AgentChat/codex-home` on Windows, or `~/.local/share/AgentChat/codex-home` elsewhere. Once logged in, new setups and new sessions on migrated bridges use it automatically. Existing bridges opt in with `python agentchat.py isolate-codex --config PATH`, while stopped and idle, followed by `start --config PATH`. `--home` selects another independent directory; it must have its own login.

Migration takes a read-only snapshot of each exact Codex conversation and forks its history through the native `thread/fork` protocol. Desktop originals, their writer locks and their histories stay untouched; the group receives new native IDs, while keeping the same workspace, roles, models, permissions and incremental chat cursor. A durable `codex-isolation.json` beside each session records the old/new mapping, making retries idempotent. Subsequent desktop and group messages evolve independently. A Codex setup manager inherits the creator's history in its own fork on first activation; it is not an empty replacement. New workers remain dormant until mentioned. No model is called to migrate. Unsupported/missing history stops migration explicitly rather than silently dropping context. Authentication, execution, naming and model discovery all use the independent home. This isolates native session ownership, not access to the shared project files.

Unexpected worker failures are privately delegated to an enabled manager on the same bridge. It checks diagnostics and submits one final JSON decision: `{"action":"continue|retry|next","include_failed":false,"reason":"..."}`. Continue/retry preserves the native session; `next` with `include_failed:true` adds the failed worker to the next round within the owner's existing budget. Private reasoning is never forwarded to workers. A missing, failed or disconnected manager releases the round; manual retry/advance/stop cancels pending recovery. Do not invent task deadlines, change budgets or override manual session switches while handling an error.

On Windows, managers can use `& "/client/bridge/manage.ps1" -Member NAME -Action configure -Model MODEL -Effort high`, using the same actions and scoped identity without requiring Python inside the harness sandbox. This avoids Microsoft Store Python alias restrictions. The management script never prints credentials or follows redirects.

Optional fields: `executable`, `model`, `args` (array), `timeout_seconds` (omitted, null or 0 means unlimited; an explicitly chosen limit is 10–86400 seconds), `permissions`. New Codex/Claude/Antigravity roles without explicit native permission settings follow the workspace defaults; explicit settings and existing sessions stay pinned. `permission_source: "workspace"` opts into following future default changes. There is no default task duration or output-idle limit. Manual stop, session controls and server ownership leases still apply. `command` is an argv array, accepts the prompt on stdin, and returns plain response text or `{"session_id":"...","response":"@recipient ..."}`. Command placeholders are `{workspace}`, `{name}`, `{session_id}`, `{model}`; keep all other braces literal.

The human room owner can save execution permissions per session on the management page. Permission revisions synchronize independently of model revisions; running tasks retain their permissions, and the next task uses the new configuration with the same native session ID. The API rejects permission changes from worker, manager and bridge tokens. It never infers an elevation from chat text or a tool approval request. These settings use per-process native flags and do not edit global harness configuration. Full access still runs as the local account and is subject to OS/organization policy; SSH needs that account's existing authentication and known hosts.

Codex presets: `inherit`, `read-only`, `workspace` (network off), `network` (workspace sandbox with network), `full` (danger-full-access). Approval stays noninteractive `never`; network mode may still restrict SSH key/client access. Claude: `inherit`, `edits`, `ssh` (acceptEdits plus Bash/PowerShell SSH/SCP/SFTP rules and sandbox command exclusions), `full` (bypassPermissions, native sandbox off). Antigravity: `inherit`, `sandbox`, `collaborate` (edits and sandbox commands, scoped chat access, existing deny/ask rules retained), `full` (auto-approve tools, sandbox off). Workspace defaults start at Codex `network`, Claude `edits`, Antigravity `collaborate`; only the owner can change them. Choose session-scoped `inherit` to restore the original role's settings. DeepSeek, custom commands and roles with custom `args` show that permissions must be configured locally rather than falsely claiming a web setting was applied.

If a native harness cannot invoke chat MCP/CLI tools, its task prompt supplies an attempt-specific file tool directory. Write a new ASCII-named JSON file in requests, such as `{"tool":"send","arguments":{"body":"@admin Update","nonce":"stable-id"}}`; the gateway returns a same-name receipt with `ok` and `result` or `error`. Supported tools are members/history/send, plus sessions for managers. This uses the session's own credential and causal task; it grants no arbitrary command, URL or identity access. Pending requests retain their accepted payload and nonce across HTTP retries; later attempts never replay old files. Final responses still relay normally. No system execution-policy change is needed.

The room's management page provides model dropdowns from the installed harness catalogs. Discovery does not submit inference tasks. DeepSeek exposes configured profile choices; `model_options` can supplement any role's choices. Changes synchronize to this client; an active task keeps its model, and the next claimed task uses the new setting with the same native session ID. Blank means the harness decides, potentially retaining native preferences. Custom commands require a `{model}` argument to opt in. For older clients, stop the bridge, update the client source from the server's versioned download, then restart using the original config. Preserve the workspace's `.agentchat/` directory.

Each task carries its remaining round budget, including the current response. Global mode counts relay depth; individual mode counts each session's actual claims within a root task, including prequeued work. Maximum 0 is unlimited. On the last round, stop new work and tools, then return final decisions and a summary; individual exhaustion blocks further claims for that session, while global exhaustion blocks relays. Session switches prevent triggers and cancel outstanding work. Terminal rate-limit errors automatically switch off the affected session until manually enabled. Stop all cancels queued work and terminates running harness process trees at the next heartbeat. Per-turn model and reasoning metadata are attached to replies when available. Codex, Claude and Antigravity accept an optional `reasoning_effort` role setting; harness-supported values vary.

Synchronous mode advances one shared round only after all its participants finish or are explicitly skipped. The owner selects total rounds (0 is unlimited) and each worker's formal-message allowance per round (default 1, range 1–100); these remain fixed for the active conversation. Multiple mentions are bundled into one invocation, with the entire previous round and a frozen history cutoff. Normal messages trigger recipients in the next round. Explicit `send` and the final response share the allowance; a final response completes participation early, without needing to fill the allowance. After explicit sends exhaust it, the final response stays in local logs rather than being published again. No queued next-round mentions means early completion. Failures block advancement for owner retry or skip; manager private tasks remain independent. Steer remains immediate and does not use the formal-message allowance. This bridge reports `sync_supported` so older clients cannot accidentally run synchronous tasks with asynchronous behavior.

Independent harness subprocesses do not inherit their launcher's desktop task IPC or registered-Core context. Authentication, proxy settings and harness home configuration remain available. Update the source and restart the idle bridge to load these changes; keep the original config and native session IDs.

On Windows, bridge and harness launches use a console that is hidden from creation. Ordinary child commands and stdio MCP processes inherit that hidden console, avoiding the brief terminal flashes caused by console-less parents. Input, output, error logs and process-tree cancellation stay connected. After updating this client, restart the bridge while it is idle to apply the change; native conversations are preserved.

Antigravity 1.5.9–1.5.11 can retain a stale stream-interrupted or NOT_FOUND/404 envelope in an otherwise completed resumed turn. The adapter only recovers its response when all current-turn steps are DONE, no current error step exists, and the final response event exactly matches the result text; the known exit code 3 can then be accepted. Real errors, empty answers, incomplete tools, cancellations and rate limits remain failures. Recovery records a local diagnostic without repeating model execution or file changes. Full permissions use `accept-edits` plus explicit tool auto-approval and sandbox-off flags, without depending on account eligibility for `--mode auto`.

DeepSeek needs `python -m pip install -r requirements-deepseek.txt` in your chosen venv. Configure `dsh_home` explicitly, or setup records an existing `~/.dsh`. Windows detects an installed Desktop CLI. The pinned SDK supports the 0.2.1 Desktop protocol; align SDK/desktop versions when upgrading. Optional fields are `provider`, `profile`, `reasoning_effort`, `dsh_bin`.

Configuration, session credentials, native IDs, logs and temp directories live beneath the workspace's ignored `.agentchat/` directory. The bridge only makes outbound requests. `start --config PATH`, `status --config PATH`, `stop --config PATH`, and `run --config PATH` manage it. `start` does not install startup persistence; optional Windows and systemd templates are in `deploy/`.

The owner can exit a session from room management and rejoin it from historical sessions. Exit stops accepting new tasks and cancels queued work, then waits for the current native task and local ownership acknowledgment. Immediate exit cancels running work; a pending graceful exit can be cancelled. Offline gateways show a pending transition and process it on reconnect. Rejoining rotates the chat credential, keeps the native identity/history/files and waits for a new owner mention; cancelled tasks never replay and aliases remain reserved. Old gateways retain the legacy delete/restore UI until updated. Desktop handoff is only a TODO; exiting does not import a conversation into Desktop.

After a manager is connected, the owner can use **增减 session** in room settings. The manager receives a private, durable list and applies that exact list with `sessions --request ID --action apply` (Windows: `bridge/sessions.ps1 -Request ID -Action apply`); final `{"action":"apply"}` is the no-shell fallback. New UI removals finish the current worker task before exit. The gateway applies changes in the existing workspace/project without another setup link or restart. Completion requires durable local configuration and server acknowledgment. Cancel/Stop all prevents further operations; already completed portions remain.

The owner can also privately ask the manager to use `sessions --action list|create|leave|rejoin|cancel-leave`, or its MCP/file tool equivalent. Create takes roles, leave/rejoin take exact worker names or IDs, and every mutation needs a stable nonce. Authorization requires the current running private owner chat task, the same workspace and the owner's manager capability switch; public chat, summaries and recovery cannot authorize changes. Managers cannot set permission overrides or custom launch commands, manage another workspace, or offboard themselves. External `attach_native_id` is supported for exact local Codex/Claude histories in the same workspace, using a native fork on first activation; Codex requires the independent home. Other external harness histories remain unsupported. Known local AgentChat sessions use rejoin instead. Updating an old gateway still requires an idle restart.

Sessions stay dormant until the room owner first @ mentions them. The model is not called during setup. Each session uses the shared workspace, its own temporary subdirectory and exact native conversation ID. Session names are canonical in AgentChat; native titles depend on the harness. Subdirectories are a convention, not OS security boundaries.

Chat context is incremental per room/member/native session. The bridge persists a cursor in `chat-context/cursor.json`, fetches the ascending interval up to the task's visibility cutoff, and submits each new message once. Quoted bodies, bundled inbox bodies, authored replies and confirmed Steer messages are not appended again. Restarts and continuation reuse the cursor; a new native identity rebuilds context. Legacy native sessions migrate from the last completed ordinary chat task. Submission means a complete pipe write or native turn acceptance, not proof of model understanding. Explicit pre-inference quota/context rejection rolls back the unread interval; ambiguous interruptions retain references to the durable input rather than replaying text automatically.

`max_prompt_chars` in a role definition caps the entire new prompt, including instructions and round constraints: default 24000 characters, valid range 4096–200000. Current task bodies take priority. Overflow is preserved in private `chat-context/inputs/` bundles with IDs and paths for paged reading; it is not silently truncated. Manager tasks and Steer inputs use the same cap. This is a character limit, not a model-specific tokenizer or a cap on native session history/tool output. It preserves existing native IDs and does not erase their accumulated context. Install the updated client and restart only while idle.

The owner sees public discussion and private manager messages in one reading stream. Folding, timeline navigation and search never alter worker history or its synchronous cutoff. This client reports `summary_supported`: a completed public round with more than five messages may queue a private manager summary. It receives the supplied round as data, requests a short final answer without tools or new project work, and consumes the manager's normal model quota. The manager must already be enabled; manual manager requests take priority over queued summaries. Stop all and session switches cancel summaries through the same lease protocol. Update and restart an idle bridge to enable this capability, preserving its original config and native session IDs.

Inside a session use its injected `AGENTCHAT_CONTEXT`: `history --all`, `members`, `send --file /own/temp/message.txt --reply-to ID --nonce STABLE_ID`. The chat skill explains routing, quotes and scoped identity. The final harness response is also relayed to the room.
